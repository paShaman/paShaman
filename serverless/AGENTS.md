## Как устроен tgcloud-проект

Код, который выполняется в облаке, лежит в **`tgcloud/`** проекта: `schema.js`,
`lib/`, `handlers/`, `endpoints/`. Рантайм — V8 isolate: нет `node_modules`, нет
файловой системы, доступны только `sdk` и модули проекта. `npx tgcloud` —
локальный dev-dependency, запускать через `npx` из папки проекта.

Правила, на которых легко споткнуться:

- Импорт модулей проекта — относительным путём **с `.js`** (`'../schema.js'`),
  SDK — по имени (`from 'sdk'`, `from 'sdk/db'`).
- **Каждый вызов БД асинхронный — всегда `await`** (`.all()`, `.get()`, `.run()`, …).
- **Внешних ключей нет** — `.references()` падает при объявлении; целостность
  держим в коде.
- Удаление — только через `.deprecated('reason')`; удаление объявления ничего не дропает.
- Хендлер получает payload обновления первым аргументом, полный `Update` — в `ctx.update`.
- `.tgcloud/` — машинное состояние CLI (креды, снапшот). Не читать и не править.

## Production safety — push и migrate делает только пользователь

`npx tgcloud push` и `npx tgcloud migrate` запускает **только пользователь**.
Агент не запускает их никогда: ни когда изменение выглядит готовым, ни когда без
этого «не завершить» задачу.

- Можно агенту: правки файлов, `npx tgcloud status`, `npx tgcloud diff`,
  `npx tgcloud migrate --dry-run`, `npx tgcloud run` (read-only модули).
- Нельзя: `push`, `migrate` (применяющий), `pull`, `reset`, `webhook sync`,
  `login`, `npm run deploy` (он делает `push`) и всё прочее, что меняет
  задеплоенного бота, статику или БД.
- Работа агента заканчивается локально подготовленным изменением и точной
  командой, которую пользователь выполняет сам.
